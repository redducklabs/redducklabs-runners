# ARC 0.14.2 to 0.15.1 Upgrade Design

Status: **blocked on an owner decision** (see "Decision required"). No code,
workflow or fixture in this repository has been changed for 0.15.1 yet.

Scope: Actions Runner Controller (ARC) charts `gha-runner-scale-set-controller`
and `gha-runner-scale-set`, from 0.14.2 to 0.15.1, the latest stable release.
0.15.1 is a patch release on top of 0.15.0, so every 0.15.0 change applies.

## Summary

ARC cannot be upgraded from 0.14.x to 0.15.x with a plain `helm upgrade` of
both charts on this fleet. Both the 0.14.2 controller and the 0.15.1
controller **delete** any AutoscalingRunnerSet (ASRS) whose
`app.kubernetes.io/version` label has a different major.minor than the
controller's own build, whenever they reconcile it. The scale set chart writes
that label. Upgrading either side while the other side's controller is
reconciling deletes the live ASRS, its listener, its EphemeralRunnerSet (ERS)
and the GitHub runner scale set registration.

Clean-up also depends on which controller does it. 0.15 renamed the ERS
finalizer and looks the ERS up by a fixed name, while 0.14.2 created it with
`generateName`. The 0.15.1 controller cannot finish deleting an ERS that
0.14.2 created (upstream issue actions/actions-runner-controller#4706, closed
by the maintainer with no code change; 0.15.1 contains no legacy-finalizer
handling).

Every procedure that avoids those failures stops the fleet first, so the
upgrade includes a window in which the fleet acquires no jobs. Two candidate
procedures are worked out below, neither yet rehearsed:

- **Option A, teardown and recreate.** Stop, let the 0.14.2 controller delete
  its own scale set, upgrade CRDs and the controller, recreate the scale set
  stopped, recover with the existing acknowledged Deploy. Uses only upstream
  delete and create paths; deletes and re-registers the GitHub scale set.
- **Option B, drained in-place.** Stop, switch the controller off, upgrade
  CRDs and both charts, switch the 0.15.1 controller on. Keeps the ASRS and the
  GitHub registration; leaves one empty legacy ERS that needs a narrowly
  scoped finalizer removal.

The fleet workflows cannot express either transition today, and three
existing paths would perform the destructive order by themselves once the
version pin moves: ordinary Prepare Runner Platform (controller first),
Emergency Stop and the shared re-stop `fleet_restop` (chart first, with
`--version` from the pin), and the local `deploy/deploy.sh` (unpinned chart).
Any upgrade therefore needs new code: a resumable migration operation, a
server-side migration fence, version-preserving stop writers, and a
cross-minor guard on Prepare Runner Platform. None of it is built yet.

The owner must choose Option A, Option B or deferral (Option D), and the
chosen procedure must pass a rehearsal in a disposable environment before it
is run in production.

### Version gate in both controllers

`apis/actions.github.com/v1alpha1/version.go` `IsVersionAllowed` is identical
at both tags: a resource is allowed when its version equals the build, or when
major and minor match. `autoscalingrunnerset_controller.go` (0.15.1, lines
121-138; same logic at 0.14.2) deletes the ASRS when the label is not allowed.
0.14.2 versus 0.15.1 differ in minor, so neither controller tolerates the other
chart's ASRS.

### What deleting the ASRS does

- 0.15.1 `cleanUpResources`: deletes every listener owned by the ASRS, deletes
  the ERS named exactly after the ASRS (it does not list owned sets), then
  deletes the runner scale set from the Actions service, then removes the
  cleanup finalizers from the Helm-owned Secret, Roles, RoleBindings and
  ServiceAccounts (it does not delete them).
- 0.14.2 lists every owned ERS (`listEphemeralRunnerSets`) and deletes them
  with its own finalizer `ephemeralrunner.actions.github.com/finalizer`, so it
  cleans up the generateName set it created.
- 0.15.1 ERS finalizer is `ephemeralrunnerset.actions.github.com/finalizer`;
  its deletion branch returns immediately for a set that carries only the old
  name. A pre-0.15 ERS that is garbage-collected after 0.15.1 deletes the ASRS
  stays Terminating, keeps its EphemeralRunners, and is never cleaned up (#4706).
- The recreated ASRS registers a new runner scale set (new ID) with the same
  name `redducklabs-runners` in runner group `redducklabs-private-runners`.
- Helm 3.21.4 `pkg/kube/client.go` `update` (lines 396-409) creates a resource
  of the target manifest that is missing from the cluster, so a later
  `helm upgrade` recreates a deleted ASRS.

### Rendered manifest with our values

`helm template` of `deploy/dind-values.yaml` (kube 1.36.3) differs between the
two charts only in `helm.sh/chart` and `app.kubernetes.io/version` labels, the
`actions.github.com/values-hash` value, and a new ASRS field:

```yaml
  listenerConfig:
    scaler:
      burst: 100
      qps: 50
```

The runner pod template, including the hand-rolled dind sidecar and its memory
reservation, is byte-identical.

### CRDs

All four CRDs stay at `v1alpha1` served and stored, so there is no stored
version migration. 0.15 removes the ASRS and ERS status count fields and the
matching printer columns, adds optional fields (listener `spec.phase`, ASRS and
listener `spec.listenerConfig`, ERS `spec.actionableRevision` and new status
fields), and marks formerly "required" spec fields optional. 0.15.1 changes the
CRDs from 0.15.0 only in the controller-gen annotation and tighter validation
of pod `evictionResponders` (upstream changelog).

Backward compatibility (inferred from the schemas, not exercised): objects
written under 0.15.1 CRDs remain readable under 0.14.2 CRDs; 0.15-only fields
are pruned on the next write after the 0.14.2 CRDs are reapplied. A 0.14.2
controller running against 0.15.1 CRDs has its status-count writes pruned.
0.14.2 reads those counts in two ways: as a scheduling gate
(`drainingJobs`, only for `updateStrategy: eventual`, which this repository
does not set), and in status reconciliation: its ERS `updateStatus` compares
the full desired status including counts, and its ASRS `updateStatus` compares
`CurrentReplicas` and `CurrentRunners`. With the counts pruned, those
comparisons never settle and the 0.14.2 controller would keep re-issuing status
patches. None of the procedures below runs a 0.14.2 controller against 0.15.1
CRDs while it has work to do, and runtime compatibility in either direction is
not verified.

## Outdated phase

In 0.15.1 a runner that exits with code 7 (the runner rejected its spec, which
in practice includes a runner version GitHub no longer accepts) marks the ERS
`Outdated`. The ASRS moves to `Outdated`, the listener is switched to
`Stopped`, the ERS is held at 0 replicas, and the phase stays until the runner
spec or runner metadata changes, or the ERS is deleted
(`outdatedRunnerSpecCorrected`). Upstream issue #4739 (open) asks to surface the
phase and to tell a runner-version deprecation apart from a rejected spec.

This interacts with this repository's image contract. The runner image is the
fixed canonical `registry.digitalocean.com/redducklabs/github-runner:latest`
with `imagePullPolicy: Always`. The phase is sticky in both versions, but the
exit differs. Under 0.14.2 any ASRS spec or label change cleared it, so a
Deploy, a Scale Runners bounds change or an Emergency Stop and recovery
rebuilt the set and pulled the current `:latest`. Under 0.15.1 none of those
clear it, and pushing a fixed `:latest` does not change the runner spec either,
so an Outdated scale set stays parked: the fleet stops acquiring jobs and the
existing operational levers do not bring it back. The recent outage was this
failure class (a stale runner version).

Any 0.15 upgrade must therefore add a recovery path that changes the runner
spec when the image changes. Candidates, to be chosen in the implementation
plan:

1. Deploy stamps the resolved image digest into the runner pod template (a
   template annotation, or the image reference by digest). A new image is then
   a spec change and clears the phase. This also makes every deploy record
   which image the fleet runs.
2. A reviewed workflow operation that deletes the parked ERS, which 0.15.1
   treats as corrected and rebuilds.

Option 1 is not a Deploy-only change. `scripts/validate-runner-isolation-contract.py`
requires the runner template metadata and pod spec to equal the canonical
contract exactly, including the canonical image string, for every contract
(burst, burst-stopped, drain, density and their stopped forms). A digest or
annotation added only by Deploy would make every later admission and readback
fail. The implementation must define where the resolved digest is recorded,
how the validator derives the canonical template from it, how candidate and
readback comparisons verify it on later operations and on rollback, and the
fixture changes, without weakening the other security, resource or placement
checks. Option 2 needs its own gate and must be reachable while the fleet is
parked.

`runner-status.yml` and the runner version guard should also report the ASRS
`status.phase`, so a parked fleet is visible.

## Upgrade-order analysis

The version check runs when a controller reconciles an ASRS. A controller that
is not running deletes nothing.

| Order | What happens | Result |
|---|---|---|
| Scale set chart first, 0.14.2 controller running | 0.14.2 deletes the 0.15.1-labelled ASRS and cleans up its own generateName ERS, listener and scale set registration | clean if the controller is not replaced until clean-up finishes (Option A uses the equivalent: deleting the ASRS directly) |
| Controller first, 0.14.2 scale set | 0.15.1 deletes the 0.14.2-labelled ASRS, misses the generateName ERS, deletes the scale set registration; GC leaves the ERS Terminating with its runners | #4706: stranded set and runners |
| Both in one apply | as reported in #4706: 0.14.2 starts deleting and is replaced mid clean-up | stranded sets, failed deregistrations |
| Controller off, both charts upgraded, then 0.15.1 controller on, fleet live | 0.15.1 sees an allowed ASRS, keeps its scale set ID, creates ERS `redducklabs-runners` and rebuilds the listener on it; the legacy ERS keeps its live runners and replicas | two live runner sets; legacy set unmanaged by any listener |
| Same, but fleet drained to 0/0 and zero runners first | as above, but the legacy ERS is empty at 0 replicas; 0.15.1 adds its own finalizer to it (`ephemeralrunnerset_controller.go` lines 170-182) | one empty legacy ERS to remove; no extra runners (Option B) |

At 0.15.1 a scale set is registered only when the ASRS's recorded
`runner-scale-set-id` annotation is absent or invalid (`shouldCreateScaleSet`,
`autoscalingrunnerset_controller.go` lines 209-212), so keeping the ASRS keeps
the registration.

## Safety invariants

Any implemented procedure must hold these, enforced by the API server where a
client-side check would race:

- **I1.** No ASRS is ever created, or relabelled, with an
  `app.kubernetes.io/version` minor different from the minor of the controller
  that will reconcile it.
- **I2.** The 0.15.1 controller never reconciles an ASRS while a pre-0.15 ERS
  with runners exists; the 0.14.2 controller never reconciles an ASRS while a
  0.15 ERS with runners exists.
- **I3.** No controller is replaced while the other generation's clean-up is in
  progress.
- **I4.** The fleet is at 0/0 with zero EphemeralRunners and zero runner pods
  for the whole migration; the Emergency Stop marker and fence are present
  throughout and are cleared only by the existing acknowledged Deploy.
- **I5.** An emergency stop always stops the fleet and never changes a chart
  version or recreates an ASRS.
- **I6.** Every mutation boundary is a resumable state: a cancelled or failed
  run leaves a state that the next run classifies and continues from, or fails
  closed with a named owner action.

### Server-side ARC version fence (I1)

A new permanent ValidatingAdmissionPolicy and binding, committed next to the
Emergency Stop fence, parameterised by a ConfigMap
`arc-runners/arc-version-contract` with one key, `allowed-asrs-minor`:

- ASRS CREATE in `arc-runners` is allowed only when the object's
  `app.kubernetes.io/version` label is in the allowed minor (`0.15.` prefix for
  `0.15`); an empty value denies every create.
- ASRS UPDATE is allowed only when the version label is unchanged or moves into
  the allowed minor.
- Parameter absent: allow (bootstrap and the period before the first rollout of
  this change), like the Emergency Stop fence.

In normal operation the parameter equals the running controller's minor, so a
stale or older-ref workflow cannot relabel the scale set into a minor that the
controller would delete; its Helm write fails closed instead. The migration
operation moves the parameter through the values each phase allows. Every
fleet operation's admission requires the policy, binding and parameter to equal
the committed file, as the Emergency Stop fence does today.

**What the fence can and cannot prove.** Admission reads policy parameters
from an informer cache in each API server (Kubernetes v1.36.3
`policy_dispatcher.go` `CollectParams` uses the lister). Reading the ConfigMap
back proves nothing about enforcement, and probing through the cluster endpoint
proves enforcement only on the API servers the probes reached. The production
cluster publishes one API endpoint address (`kubernetes` EndpointSlice, read
2026-11-09), and `doctl kubernetes cluster get` reports `ha` as null, so a
single API server is likely but not established. The design therefore does not
rest correctness on the fence. The fence is defence in depth; correctness rests
on three other measures:

1. **Writer coordination.** Every in-repository writer of the ASRS or the
   scale-set release (Deploy, Scale Runners, Rebalance, acceptance, drain,
   rollback, Emergency Stop and `fleet_restop`), from this change on, reads the
   migration record (below) before any Helm write and refuses, or for stop
   writers uses the bounds-only path, while it exists. The stop writers read
   the record immediately before their Helm call, but a stop that read it as
   absent can still be paused between that read and the call. Every fleet
   workflow other than Emergency Stop shares the migration's
   `runner-fleet-mutation` concurrency group and cannot overlap it; Emergency
   Stop runs in its own group by design. The migration therefore has a
   **record-write barrier**: after writing the record at S0, and before step
   1, it waits until the GitHub Actions API shows no Emergency Stop run, at any
   SHA, that was created before the record write plus a margin for API
   listing latency and is not yet completed. A stop created after that point
   reads the record as present and never reaches Helm. The Emergency Stop
   check is repeated before every later step. Runs of the other fleet
   workflows (Deploy, Scale Runners, Rebalance, acceptance, Prepare, Node Pool
   Sizing) that are queued in `runner-fleet-mutation` cannot start until the
   migration releases the group, so the migration does not wait for them
   (waiting would deadlock on its own lock). When they do start, a run at this
   change's SHA or later reads the record and refuses while it exists
   (Prepare Runner Platform included). Runs at an older SHA are not uniformly
   safe: old Deploy, Scale Runners and Rebalance fail their ARC identity gate
   on anything but 0.14.2, but old Prepare Runner Platform has no identity
   gate and would reinstall 0.14.2 CRDs and the 0.14.2 controller, and the
   version fence does not cover CRD or controller writes. Therefore the
   migration's S0 admission requires that **no** run of any workflow in
   `runner-fleet-mutation`, and no Emergency Stop run, exists queued or in
   progress at a SHA other than the migration's own; the owner cancels any
   such run before dispatching the migration (the run lists them by id).

   Detection alone cannot keep an old Prepare out after S0: a migration that
   fails or is cancelled releases the concurrency group to whatever is queued.
   The exclusion for Prepare is therefore persistent and independent of the
   migration run: the migration lives in its own workflow file (not in Prepare
   Runner Platform), and the owner disables the Prepare Runner Platform
   workflow at repository level (`gh workflow disable`) before dispatching
   it. A disabled workflow cannot be dispatched from any ref, and the state
   survives migration failure and cancellation. S0 admission and every later
   step require, through the Actions API, that Prepare Runner Platform is
   disabled and that no run of it is queued or in progress; the owner
   re-enables it only after the migration record is deleted. The repeated
   any-SHA check still covers the other fleet workflows, whose old code fails
   its identity gate.

   Residual, stated for the owner: an Emergency Stop dispatched from a
   pre-change branch after the barrier is not excluded (Emergency Stop must
   stay enabled). Its Helm write is bounded by the version fence (sampled) and
   by measure 2; the runbook requires dispatching fleet workflows from `main`
   only.
2. **Source controller off before any irreversible step.** After teardown
   (Option A) or before relabelling (Option B) the source controller is
   switched off and stays off. A source-labelled write that slips past both
   measures above can no longer produce a source-generation ERS; the worst
   case is that the target controller deletes that ASRS, which strands
   nothing. Under Option A, step 7 recreates it. Under Option B it also
   deletes the preserved registration, which B detects (steps 5 and 7 compare
   the recorded UID and scale-set ID) and fails closed on; the owner may then
   convert the migration to Option A (below), which recreates the scale set
   with a new registration.
3. **Re-validation after switch-off.** The step that switches the source
   controller off completes only when it re-reads the state the next step
   relies on (Option A: no ASRS, ERS or listener; Option B: ASRS UID and
   labels as recorded, only the recorded ERS) after waiting at least the API
   server request timeout (60 s by default), so that any write admitted before
   that point has persisted or failed.

The fence barrier, run after every parameter change, uses server-side dry-run
probes modelled on the existing `fleet_fence_wait`, with exact old and new
labels per phase:

| Phase | Probes that must be denied | Writes that must stay allowed |
|---|---|---|
| frozen (parameter empty) | CREATE of a probe ASRS labelled source; CREATE labelled target; UPDATE of the live ASRS (if any) changing its label from source to target | UPDATE of the live ASRS with its label unchanged (controller and bounds-only writes) |
| target allowed, before relabel (Option B step 4) | CREATE labelled source; UPDATE of the live ASRS changing its label from source to a different source-minor patch version | UPDATE source to target (the relabel itself); unchanged-label UPDATE |
| target allowed, after relabel or recreate | CREATE labelled source; UPDATE changing the label from target to source | unchanged-label UPDATE |

A required number of consecutive denials over a minimum interval is needed;
any allowed forbidden probe restarts the count, and no convergence within a
bounded time fails the run closed. An allowed no-op UPDATE is the expected
result, not a fence failure. Before production use, the implementation plan
must either establish that the control plane is a single API server (from
DigitalOcean's documented behaviour for non-HA clusters and the cluster's HA
setting) or accept, as an owner decision, that the barrier samples one backend
and correctness rests on the three measures above.

## Options

Options A and B are both implemented as one new, fleet-locked, explicitly
confirmed workflow (proposed: a new `.github/workflows/arc-minor-migration.yml`
on `ubuntu-latest`, in the `runner-fleet-mutation` group, separate from
Prepare Runner Platform so that Prepare can be disabled during the
transition) with inputs `option` (A or B), and source and target versions
from an allow-list (`0.14.2` and `0.15.1`, in either direction). Ordinary fleet admission is not relaxed: every other operation
still requires both releases, the controller and the ASRS label at one
version, plus both fences. The migration uses its own bracket, because the
shared `fleet_helm_bracket` refuses to run while a stop marker exists
(`scripts/lib/fleet-ops.sh` lines 157-159) and the migration runs only while
one exists.

**Migration record.** At S0 the run writes a ConfigMap
`arc-runners/arc-minor-migration` holding: option, source, target, the run id
that started it, the S0 ASRS UID and `runner-scale-set-id` annotation, the S0
ERS and listener names, and `completed-step`. A re-dispatched run must match
option, source and target exactly or fail closed; it never re-baselines the
S0 identities. The record is deleted only after the completion predicate
holds, as the last write of the migration.

The record is also an admission exclusion. While it exists (or cannot be
read), the pool-state gate refuses every operation except the matching
migration continuation and read-only diagnostics; in particular, acknowledged
Deploy and rollback may not delete the Emergency Stop marker, even when
releases, controller and ASRS label already agree (as they do after Option B
step 6). Emergency Stop and `fleet_restop` use only the marker and bounds-only
path while it exists. The migration's final step runs the ordinary gate's
classification read-only, then deletes the record; only after that can the
acknowledged Deploy reopen the fleet.

**Classification.** Steps run in a fixed order. Each step has an idempotent
action and a completion predicate over live state. A run reads
`completed-step` = k and evaluates step k+1's completion predicate: if it
holds, the run records k+1 and moves on; otherwise it re-runs step k+1's
action. Live state that satisfies neither step k's completion predicate nor
any in-progress form of step k+1 fails closed with the observed state. The
record is advanced only after the completion predicate is observed, so
cancellation between an action and its record write repeats an idempotent
action rather than skipping one. This gives exactly one classification for
every snapshot, including snapshots taken mid-write.

**Helm status handling.** `deployed` proceeds. `failed` on the release that the
current step writes permits re-running that step's upgrade (Helm allows
upgrading a failed release). `failed` on any other release, and any `pending-*`
status, fail closed with an owner action: clearing them means rolling back or
editing release metadata, which this repository does not automate.

**Entry state S0** (both options): Emergency Stop marker present and the
Emergency Stop fence exact; ARC version fence exact with `allowed-asrs-minor`
equal to the source minor; ASRS present, labelled with the source version, in
the canonical `burst-stopped` state (0/0); both releases at the source version
and `deployed`; controller at the source version and Ready; zero
EphemeralRunners and zero runner pods; no migration record. Getting there is
the existing Emergency Stop plus waiting for in-flight jobs to finish.

**Controller switch-off.** The controller chart renders
`replicas: {{ default 1 .Values.replicaCount }}`, so `replicaCount=0` renders
one replica (verified by rendering both charts). The switch-off is therefore a
direct scale of the controller Deployment
(`app.kubernetes.io/name=gha-rs-controller`, exactly one, in arc-systems) to 0
by the migration operation, followed by waiting until no controller pod exists
(terminating pods included). The next `helm upgrade` of the controller
restores the chart's replica count, because Helm 3's three-way merge patches
live drift back to the rendered manifest.

### Option A: teardown and recreate

| Step | Action (idempotent) | Completion predicate | In progress / failure |
|---|---|---|---|
| 1 freeze | set `allowed-asrs-minor` to empty; barrier | probes denied per the barrier | barrier timeout fails closed |
| 2 teardown | delete the ASRS if present and not Terminating; wait | no ASRS, no ERS labelled `actions.github.com/scale-set-name=redducklabs-runners`, no listener for it, after the barrier's request-timeout wait | ASRS or ERS Terminating under the source controller: wait; still present at timeout: fail closed, controller untouched (deregistration failure, as in #4706) |
| 3 source off | scale the controller Deployment to 0 | Deployment `spec.replicas == 0`, no controller pod; re-check no ASRS, ERS or listener | pods terminating: wait |
| 4 CRDs | server-side apply the target CRDs | all four Established and equal to the target chart's files | partial apply: re-apply |
| 5 target on | `helm upgrade --install arc` at the target, `--wait` | controller release at target and `deployed`; Deployment Ready at target | release `failed` or rollout not Ready: re-run step 5 |
| 6 unfreeze | set `allowed-asrs-minor` to the target minor; barrier (a CREATE labelled with the source minor is still denied) | probes behave as required | |
| 7 recreate | `helm upgrade` the scale-set release to the target chart rendered from committed `deploy/dind-values.yaml` with 0/0, behind the manifest-hash post-renderer (not `--reuse-values`, which keeps the old chart's defaults and is subject to the Ruling 47 int/float quirk) | scale-set release at target and `deployed`; ASRS present, labelled target, 0/0 | release `failed`: re-run step 7 |
| 8 settle | wait | direction-aware, see below; ordinary gate classifies `burst-stopped` with every identity at the target | timeout fails; resume |
| 9 close | delete the migration record | record absent | |

Any source-labelled ASRS that a stale writer managed to create between steps 2
and 6 finds no source controller to build an ERS for it; the target controller
deletes it on its first reconcile (version mismatch) with nothing else to
clean up, and step 7 recreates the release's ASRS.

Step 8 completion, target 0.15.1: ERS `redducklabs-runners` at 0 replicas,
the listener's `spec.ephemeralRunnerSetName` equal to it, ASRS phase
`Running`. Target 0.14.2: exactly one ERS owned by the ASRS (generateName
`redducklabs-runners-`) at 0 replicas, no ERS of the source generation, the
listener referencing that ERS, ASRS phase `Running`.

Consequences: the GitHub runner scale set is deleted and re-registered with a
new ID under the same name and runner group. The ASRS is absent between steps
2 and 7, so the ordinary gate cannot see the fleet then; only the migration
operation and Emergency Stop's bounds-only path (which finds nothing to patch)
act in that window.

### Option B: drained in-place

| Step | Action (idempotent) | Completion predicate | In progress / failure |
|---|---|---|---|
| 1 freeze | set `allowed-asrs-minor` to empty; barrier | probes denied | barrier timeout fails closed |
| 2 source off | scale the controller Deployment to 0 | `spec.replicas == 0`, no controller pod | pods terminating: wait |
| 3 CRDs | server-side apply the target CRDs | all four Established and equal to the target chart's files | partial apply: re-apply |
| 4 allow relabel | set `allowed-asrs-minor` to the target minor; barrier (relabel to the source minor and CREATE with the source minor denied) | probes behave as required | |
| 5 relabel | `helm upgrade` the scale-set release to the target chart, 0/0, rendered from committed values behind the hash post-renderer | release at target and `deployed`; ASRS labelled target, UID and `runner-scale-set-id` equal to the record | release `failed`: re-run step 5; UID or ID differ: fail closed |
| 6 target on | `helm upgrade arc` to the target chart, `--wait` | controller release at target and `deployed`; Deployment Ready | release `failed` or rollout not Ready: re-run step 6 |
| 7 adopt | wait | exactly one target-generation ERS owned by the ASRS (named `redducklabs-runners`) at 0 replicas, the listener referencing it, ASRS phase `Running`, ASRS UID and `runner-scale-set-id` equal to the record; the only other ERS allowed is the recorded source-generation set, empty, Terminating or not | timeout fails; ID changed: fail closed (registration was not preserved); any unrecorded ERS: fail closed |
| 8 legacy | for the recorded source-generation ERS: require zero EphemeralRunners owned by it and `spec.replicas == 0`; delete it if not already Terminating; wait until the target controller has removed any finalizer of its own; then remove the remaining source-generation finalizer with a JSON patch whose `test` op requires the finalizer list to be exactly that finalizer | the recorded source-generation ERS no longer exists, and Option A's step 8 predicate for the target holds | any other finalizer, any owned runner, or a failed `test` fails closed |
| 9 close | run the ordinary gate classification read-only (`burst-stopped` at the target); delete the migration record | record absent | |

Step 8 is the narrow, reviewed finalizer removal the upstream maintainer and
the #4706 reporter describe, applied only to an empty, deleting set whose
finalizer list is verified in the same request. Option B runs only in the
forward direction (source 0.14.2, target 0.15.1), so the remaining finalizer
is always `ephemeralrunner.actions.github.com/finalizer`.

Consequences: the ASRS, its scale set ID, the Helm-owned Secret, Roles and
ServiceAccount are kept; nothing is deregistered from GitHub because no runner
exists. Nothing in the namespace is reconciled between steps 2 and 6, which is
safe only because the fleet is empty. B relies on more cross-generation
behaviour (in-place ERS creation, listener replacement, legacy-set
reconciliation) than A, all read from source, none exercised.

**Converting B to A (forward direction only).** If forward Option B (source
0.14.2, target 0.15.1) fails closed after step 6 because the ASRS was deleted,
is Terminating, or was replaced (UID or scale-set ID differ from the record),
the owner may re-dispatch the migration with `option: A` and an explicit
`convert_from_b: true` confirmation. The run accepts this only when the record
says forward option B with `completed-step` 6 or later. Conversion is a
persisted sub-sequence in the B record (`converting: true`, with its own
completed sub-step), so cancellation cannot skip a phase:

0. Replacement teardown: if an ASRS exists and is not Terminating, delete it
   only when all of these hold in the same read: it is labelled with the
   target version; it carries the Helm ownership annotations of release
   `redducklabs-runners` in `arc-runners`; it is at 0/0; no EphemeralRunner
   and no runner pod exists for the scale set. Otherwise fail closed. The
   running target controller performs its clean-up.
1. Legacy cleanup: B's step 8 action and guard on the recorded 0.14.2 ERS.
2. Drain: wait until no ASRS, no ERS and no listener exist. The 0.15.1
   controller's ASRS deletion waits only for the fixed-name ERS and then
   deletes the registration; the legacy ERS no longer blocks anything after
   sub-step 1.
3. Rewrite the record to option A at `completed-step` 6 (freeze, teardown,
   source off, CRDs, target controller and unfreeze all hold), keeping the S0
   identities for diagnosis, and continue at A's step 7, which recreates the
   scale set with a new registration.

Conversion is not offered in the reverse direction. There, the 0.14.2
controller's ASRS deletion waits for every owned ERS, including the 0.15 set
whose finalizer it cannot remove, so recovery needs a different order; reverse
Option B is not offered at all (see "Rollback").

### Option C: upstream procedure (uninstall and reinstall)

docs.github.com, "Upgrading ARC": uninstall every scale set, wait for clean-up,
uninstall the controller, delete the `actions.github.com` CRDs if they
changed, reinstall. Deleting CRDs deletes every ARC object. This repository has
no first-install path for the scale set by design (Ruling 15), so this needs a
new reviewed bootstrap workflow. Its clean-up step is Option A's step 2, with more
destruction around it. Not recommended.

### Option D: defer

Stay on 0.14.2 and track #4706 and #4739. The runner version that caused the
recent outage comes from this repository's image, not from the ARC chart, so
deferring does not reintroduce that outage. The cost is falling behind ARC
fixes (0.15.0 contains many reconcile and clean-up fixes) and a larger jump
later, which will need the same migration operation.

Upstream also documents a high-availability layout (a second scale set in
another cluster or runner group) to avoid the window. It is outside this
fleet's contract (one release, one namespace, one runner group) and is not
evaluated here.

### Comparison

| | A | B |
|---|---|---|
| Outage | stop through acknowledged Deploy | same |
| GitHub registration | deleted, re-registered with a new ID | kept |
| Kubernetes writes beyond Helm, CRDs and fence parameters | one ASRS delete, one controller scale to 0 | one controller scale to 0, one legacy ERS delete, one `test`-guarded finalizer removal |
| Upstream paths relied on | delete under the owning controller; create from scratch | in-place adoption of 0.14.2 objects by 0.15.1 |
| Rollback | reverse A, clean (each controller deletes its own generation) | reverse A; reverse B is not offered |

## Decision required

1. Option A, Option B, or defer (Option D). The author's recommendation is to
   rehearse both A and B in a disposable environment, choose B if its
   rehearsal passes (it keeps the registration and the gate's view of the
   fleet), and otherwise A.
2. If A: accept that the GitHub runner scale set is deleted and re-registered
   with a new ID under the same name and runner group.
3. If B: accept one reviewed, `test`-guarded finalizer removal on the empty
   legacy ERS, performed by the workflow.
4. The Outdated-phase recovery mechanism that must ship with the upgrade
   (digest stamping with the validator changes, or an ERS delete operation).
5. A disposable environment and a test GitHub organisation or repository with
   its own credentials for the rehearsal.
6. Unless the control plane is established to be a single API server, accept
   that the version-fence barrier samples one backend and that correctness
   rests on writer coordination, source controller switch-off and
   re-validation ("What the fence can and cannot prove").
7. Disable Prepare Runner Platform for the whole transition, and accept the
   stated residual: an Emergency Stop dispatched from a pre-change branch
   during the transition is not excluded, only bounded.

## Stop writers (I5)

There are two stop writers: the Emergency Stop workflow's Helm write, and
`fleet_restop` in `scripts/lib/fleet-ops.sh` (used by `fleet_stop_fence` after
every fleet Helm write when the marker is present or unreadable). Both pin the
chart version today. Required design for both:

1. Write or keep the marker first (unchanged, Ruling 33).
2. Bounds-only write: if the ASRS exists, patch only `spec.minRunners` and
   `spec.maxRunners` to 0 (merge patch on the existing object). This cannot
   create the ASRS or change its labels, and the Emergency Stop fence admits
   it. An absent ASRS means there is nothing to stop.
3. Helm write, unchanged in shape (`--reuse-values`, 0/0, Ruling 26), only
   when every one of these reads succeeds and agrees: the live release's chart
   is `gha-runner-scale-set-<v>` with `<v>` in the allow-list; the live ASRS
   label is `<v>`; the controller release is at the same minor; and no
   migration record exists (read successfully and absent). It uses
   `--version <v>` from the live release, never the repository pin.
4. Otherwise the Helm write is skipped and the run fails after the stop,
   reporting that the fleet was stopped by the bounds-only patch and Helm
   values were not updated. No version is guessed.

The skipped-Helm outcome leaves Helm values and manifest at non-zero bounds
with a 0/0 ASRS. The gate must classify that as a new stopped variant, admitted
only while the marker exists and only for acknowledged Deploy and rollback,
which then write through Helm as today.

Workflows dispatched from a ref older than this change still pin the chart.
On an API server that enforces the current fence parameter, their relabelling
writes are denied and a stale stop fails closed instead of deleting the ASRS.
Enforcement on every production API server is not established (see "What the
fence can and cannot prove"), so on an unobserved backend the write could be
admitted and the target controller could delete the ASRS (and, for Option B,
its registration), with the detection and recovery described there. The
procedure therefore requires that fleet workflows are dispatched from `main`
only, and the runbook says so.

## Prepare Runner Platform guard

The ordinary `prepare-runner-platform.yml` run (namespace, registry secret,
CRDs, controller) must refuse a cross-minor change. It may proceed only when:

- bootstrap: no ARC releases, no ASRS and no ARC CRDs exist; or
- same minor: the controller release, the scale-set release and every ASRS
  label are already at the target minor.

In every other case it fails before writing and names the migration operation.
It also reconciles the ARC version fence and its parameter to the target
minor, which is only correct under one of the two cases above.

## deploy/deploy.sh

`deploy/deploy.sh` runs an unpinned `helm upgrade --install` of the scale set
outside the gate and the fleet lock. Policy already forbids using it for
production; the implementation retires it (the script exits with a pointer to
the workflows) and removes documentation that presents it as a deployment
path.

## Rollback to 0.14.2

Rollback crosses the minor version in the other direction and runs the same
migration operation with source 0.15.1 and target 0.14.2, from a commit that
reverts the version pins but keeps the migration operation, both fences and
the stop-writer changes. Reverting the whole upgrade commit would remove the
operation needed to roll back.

- Reverse A: teardown under the 0.15.1 controller is clean, because 0.15.1
  deletes its own fixed-name ERS with its own finalizer; then 0.14.2 CRDs,
  controller and a recreated 0.14.2 scale set.
- Reverse B is not offered. The 0.14.2 controller would list the 0.15 ERS
  `redducklabs-runners` as owned, find no `runner-spec-hash` annotation,
  create a new generateName set and delete the 0.15 one, which then waits on a
  finalizer 0.14.2 does not know; and any 0.14.2 ASRS deletion in that state
  waits for every owned ERS, so it cannot complete until that finalizer is
  removed. Reverse A avoids all of this and is the rollback for either forward
  option. The migration operation rejects `option: B` with source 0.15.1.

The migration record's source, target and option are part of every
re-dispatch check, so a rollback cannot be started on top of an unfinished
forward migration; the forward run must reach its completion predicate first,
or fail closed and be resolved by the owner.

Reapplying 0.14.2 CRDs is accepted by the API server (same served and stored
version); 0.15-only fields are pruned on the next write. This is inferred from
the schemas, not exercised.

## Rehearsal before production

Source reading cannot establish the behaviour these procedures depend on. The
chosen procedure, forward and reverse, must run in a disposable Kubernetes
cluster registered to a test GitHub organisation or repository with its own
credentials (never the production token), using the same workflows or the same
scripts. Pass criteria:

1. Start at 0.14.2 with one job running and one queued at the time of the
   stop; the running job completes; after recovery the queued job runs on the
   upgraded fleet.
2. No ERS, EphemeralRunner or listener is left Terminating or ownerless; no
   runner registration is left in the GitHub runner list.
3. Emergency Stop dispatched at each state boundary leaves a stopped fleet
   and a state the migration resumes from.
4. Cancelling the migration after each write and re-dispatching it completes.
5. An Emergency Stop dispatched from a pre-change ref during the migration
   has its relabelling write denied by the version fence on the rehearsal
   cluster. This shows the policy works; it does not prove enforcement on
   every production API server.
6. The reverse migration returns to a canonical 0.14.2 `burst-stopped` state
   and acknowledged Deploy recovers it.
7. The Outdated recovery mechanism clears a parked scale set (simulated by a
   runner image that exits with code 7).
8. Every version-fence barrier holds: a forbidden probe is denied before the
   run proceeds, and a stale writer started just before a parameter change
   either completes before the post-barrier re-read or is denied, on the
   rehearsal cluster's API server topology (recorded with the result).
9. Option B only: the ASRS UID and `runner-scale-set-id` recorded at S0 are
   unchanged at completion, including after a cancelled and re-dispatched run.
10. With the migration record present (for example after cancelling Option B
    at step 6 or 7), acknowledged Deploy is refused and leaves the marker in
    place, and Emergency Stop performs only its marker and bounds-only writes.
11. Normal path: an Emergency Stop at the migration's SHA, paused after
    reading the record as absent and before its Helm call, holds the
    migration at the record-write barrier until it completes.
12. Fault injection (harness bypasses the barrier, forward B only): the same
    paused stop released after step 6 and before closure has its relabel
    either denied by the fence or detected by B's identity check, and the
    B-to-A conversion completes, including when cancelled between its
    sub-steps. A release after closure is outside the design's guarantees
    (the record is gone) and is not a pass criterion.
13. A Deploy dispatched from `main` between migration start and the record
    write waits in the concurrency group and, when it starts, refuses while
    the record exists; a Deploy at a pre-change SHA fails its identity gate.
14. A queued or in-progress Prepare Runner Platform run at any SHA, or the
    workflow being enabled, blocks S0 admission and every later step; while
    it is disabled, a dispatch from an old branch is rejected by GitHub,
    including after the migration fails or is cancelled after the target
    controller starts.
15. B-to-A conversion completes from each accepted state: ASRS absent,
    Terminating, and a healthy target-labelled replacement with a changed UID
    or scale-set ID, with cancellation around the delete, the legacy cleanup,
    the record rewrite and the recreation.

## Risks

- Outage length depends on how long in-flight jobs take to finish after the
  stop; the operator chooses when to start.
- The source-generation controller could fail to deregister a runner during
  teardown (as in #4706); Option A step 2 fails closed with that controller still running
  rather than proceeding.
- Behaviour that depends on the GitHub service (queued-job pickup, scale set
  re-registration) can only be tested against a real organisation.
- 0.15.0 is a large release (about 70 changes) with a known upgrade defect
  (#4706) and an open usability issue around the Outdated phase (#4739).
- The ARC version fence is a new admission dependency for every fleet
  operation; a missing or drifted fence blocks fleet operations until Deploy or
  Prepare reinstalls it.
